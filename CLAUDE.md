# CLAUDE.md

This file gives Claude Code (claude.ai/code) guidance for the `MA-HTML-Player` project.

## Project

A self-hosted HTML dashboard controller for [Music Assistant](https://www.music-assistant.io/) (MA). The file `ma-dashboard.html` runs directly in the browser — even on old iPads with iOS 9 / Safari 9 — and talks directly to the MA WebSocket API. It replaces an earlier version that mediated through Home Assistant REST services and offered only very limited functionality.

## Purpose and feature set

The app is built as an app-like layout with five pages, switched between via a footer with five plain icon buttons (no text labels): **Lounge**, **Now Playing**, **Radio**, **Library**, **Search** (see "Page router (footer navigation)").

- **Direct MA control** over WebSocket (`/ws`) with long-lived token authentication.
- **Player selection** as a station-like bar at the top of the header (all players, or a configurable whitelist). Tapping the already-active station opens a grouping menu: current group members can be removed there, and other groupable players can be added.
- **"Quick Actions" menu**: the button next to the station bar carries the visible text "Quick Actions ❯" and opens the same dropdown as before (the "All players" list), extended with a "Quick Actions" section holding two square buttons — "Play Music" and "Sleep" (see "Quick Actions"). The same two buttons are duplicated on the Lounge home page (see below) — same shared `doPlayMusic()`/`doSleep()` functions, just reachable from two places, since both are genuinely useful on their own.
- **Page titles**: each page shows a heading (`.page-title`) at the top — "Lounge", "Radio", "Collection" or "Search" statically, dynamically "Now Playing" or, during playback, "Now Playing - {source} - {title}" on the Now Playing page (see "Page router (footer navigation)" and "Now Playing: full screen and gradient").
- **Lounge page** (footer: first icon, leftmost — the "home" page): Quick Actions (Play Music/Sleep, see above) plus two best-effort "what to play" sections — recently played items grouped by provider, and MA's own cross-provider recommendations, both filtering out provider-generated "radio"/"mix" playlist shells (see "Lounge (home page)").
- **Now Playing page** (footer: second icon): a full-screen, centered view with large cover, title, artist, album, progress bar, transport, Shuffle/Repeat and volume. The page background tints itself with colors extracted from the cover when possible (see "Now Playing: full screen and gradient"). A third icon next to Favorite/Add-to-playlist opens the queue as a slide-in panel from the right (see "Queue: shared panel that shifts the content"), which also carries the Radio Mode button (see "Radio Mode"). For group/sync players, an expandable menu lets you control each group member's volume individually. The cover crossfades on track change instead of being swapped hard (see "Cover crossfade and queue slide").
- **Radio page** (footer: third icon): on the left, the same compact playback controls as Library/Search (see "Page router (footer navigation)"); on the right, tiles of favorited radio stations grouped by country (best-effort, plus a small manual mapping list for stations without country metadata, see "Radio"), with the station's artwork as the tile background. Tapping plays the station immediately and switches to the Now Playing page.
- **Collection page** (footer: fourth icon, titled "Collection" in the UI — see below): the same two-column layout as before, now with noticeably narrower, compact playback controls on the left (see "Page router (footer navigation)"), leaving more room for the list on the right. Quick access to saved playlists, artists, albums, tracks, radio, podcasts, audiobooks — including a favorite-heart indicator. A "Favorites only" toggle chip, five sort chips plus a direction toggle (see "Sorting"), and a music-source filter (see "Music source filter"). A button set apart from the filter chips opens the queue as its own slide-in panel (see "Queue: shared panel that shifts the content").
  - **Title "Collection" instead of "Library"**: only the visible page title (`pagetitle.library`) and the (currently unused, since the footer is icon-only) `tab.library` string were renamed — internal identifiers (`LIB_TYPES`, `currentLibType`, `#pageLibSearch`, `lib.*` keys, this CLAUDE.md) still say "library", to avoid a large, risky rename across the codebase even though only the English UI text changes.
  - **Footer icon**: `svgIcon('library')` now shows three standing record "spines" on an implied shelf instead of four equal-height bars — the third is tilted via `transform="rotate(-14 …)"` around its own bottom edge so it looks like it's leaning, rather than just floating at an angle.
- **Search page** (footer: fifth icon): the same two-column layout with the same compact controls on the left; on the right, search across tracks, albums, artists, playlists, radio, podcasts, audiobooks, also with a music-source filter.
- **Settings**: a gear button in the header next to the theme/accent-color switches opens a panel with two settings — a default music source for Library and Search, and the "Side"/"Banner" playback-controls position for Radio, Library and Search (see "Settings").
- **Volume nudge**: every volume slider (mini, full-screen, Banner, Radio) carries a small `−`/`+` button on each side for precise single-step adjustment (see "Page router (footer navigation)").
- **Navigation** within Library/Search: Artist → Albums + Top tracks, Album → Tracks, Playlist → Tracks, Podcast → Episodes. Opening a detail view from Library or Search keeps the originating footer entry visually active; "Back" returns there when leaving the detail view (see "Page router (footer navigation)").
- **Lazy-loaded detail tabs** on the artist view: "Top tracks" (real top/featured tracks, `music/artists/top_tracks`), "Tracks" (full track list, `music/artists/artist_tracks`) and "Albums" only load when their tab is opened. For artists coming from the library, the real streaming provider from `provider_mappings` is used automatically instead of the pseudo-provider `library`, since the latter only returns library-linked entries server-side (see "Library items and provider resolution").
- **Music source filter** in Library and Search: an extra chip row that shows only hits from a specific streaming provider (Tidal, YouTube Music, SoundCloud, …), already populated at startup instead of only after the first search (see "Music source filter").
- **Filter/Sort/Source kept separate**: in Library and Search, the media-type filter chips, the sort chips and the music-source chips sit in three visually separated sections (thin divider plus a small "Filter"/"Sort"/"Source" label per section), no longer mixed into one row (see "Music source filter").
- **Sorting**: Library, Search, and the "Tracks"/"Albums" tabs of the artist view offer chips to switch the sort order. Sorting happens client-side via `sortMediaItems(items, mode, dir)`. The "Top tracks" tab is deliberately not sortable, since its order is the server's popularity ranking; likewise, track numbers/playlist order stay untouched in other detail views.
  - Search and the artist view still only use "Name"/"Year" (`SORT_MODES`; Search additionally has "Relevance" as its default, via `SEARCH_SORTS`).
  - The Collection page has its own, larger list (`LIB_SORT_MODES`, independent of `SORT_MODES`): "Name", "Year", "Album Artist", "Last Played", "Play Count". `albumArtistOf(it)` resolves the album's own artist for this (`it.album.artists[0]`/`.artist`, falling back to `artistsOf(it)` for items with no nested `.album`, e.g. albums themselves). `last_played`/`play_count` are MA library-row statistics — the same "present on every item in practice, 0/no-op otherwise instead of erroring" assumption as `timestamp_added` (see "Add to Playlist").
  - Alongside that, a dedicated direction-toggle chip (`.filt.dir`, a plain arrow glyph `↓`/`↑`, `libSortDir` ∈ {1, -1}) instead of one chip per mode × direction — it persists across sort-mode changes. `dir` in `sortMediaItems()` simply reverses whichever mode's comparison result; what direction "1" means for a given mode (e.g. Year/Last-Played/Play-Count already descending by default, Name/Album-Artist ascending) doesn't change — it only mirrors existing behavior rather than redefining it.
- **Action sheet** per medium: Play now, Gently play now (see below), Play next, Add to queue, Add to playlist, Favorite/unfavorite, Open/Artist/Album, View metadata (see "View metadata").
- **Add to Playlist** from both the action sheet and the Now Playing cover. In the sheet, playlists are grouped by provider (a subheading per provider); within a group, a chip switches between "Recently added" and "Alphabetical" (see "Development and customization"). A successful add is confirmed both directly on the tapped playlist button (a brief "✓ Added" state) and via a toast.
- **Queue**: view, jump to a track directly, delete individual entries, clear the queue — as a shared slide-in panel, reachable from both the Collection and Now Playing pages, not as its own footer entry (see "Queue: shared panel that shifts the content").
- **Favorite heart** both in the Now Playing area and in every detail view.
- **Dark/Light mode**: follows the system setting by default (`prefers-color-scheme`), switchable via a header button; a manual choice is remembered in `localStorage` and permanently overrides the system (see "Dark/Light mode").
- **Accent color**: selectable via a color wheel in the header — either "Dynamic" (first swatch, rainbow swirl; `--accent` is then determined live from the current track's artwork) or a fixed preset color (default: White; also Blue, Light Blue, Light Orange). The choice is remembered in `localStorage` (see "Accent color").
- **Language**: English only. There is no longer a DE/EN switcher; all text comes from a single `STRINGS` dictionary.
- **Fonts**: Roboto Mono (titles, labels/chips, numbers) and Roboto (body text) instead of plain iOS system fonts; the "Lounge Music" brand wordmark (`.brand`) deliberately gets a flourished script font (Mrs Saint Delafield) as its one exception — see "ES5/iPad compatibility" and `fonts/`.

## Architecture

### Why WebSocket instead of HTTP JSON-RPC?

MA offers both the WebSocket endpoint `/ws` and a POST route `/api` for JSON-RPC. The POST route sends **no CORS headers**, so XHR/fetch from a different origin (e.g. `file://` on an iPad, or any local web server) fails at the preflight. WebSocket handshakes aren't subject to the same-origin policy, so the file works from anywhere.

### Communication flow

1. `connect()` opens `ws://<host>/ws` or `wss://<host>/ws`.
2. The first command sent must be `auth` with `token` (`send('auth', { token: CFG.TOKEN }, …)`).
3. After successful authentication, all players and queues are loaded initially (`bootstrap`).
4. All further state changes arrive as server events (`player_updated`, `queue_updated`, `queue_time_updated`, `queue_items_updated`, `media_item_updated`).

### Partial-response handling

Long lists (e.g. `players/all`, `player_queues/items`, search results) can arrive in chunks of up to 500 entries with `partial: true`. Only the final, non-partial message completes the response. The client collects these in `pending[id].chunks` and then delivers the assembled array to the callback.

### ES5/iPad compatibility

- No CSS Grid, no `@supports`. CSS custom properties (variables) are the one deliberate exception — see "Dark/Light mode" — because Safari has supported them since 9.1 (iOS Safari 9.3), which is the project's minimum requirement anyway (see "Troubleshooting").
- `display: -webkit-flex` and `display: flex` with vendor prefixes.
- No arrow functions, no `fetch`, no `const`/`let`, no `Promise`, no `class`, no `Object.assign`.
- `XMLHttpRequest` only for the initial `/info` request (to read the `Date` header for clock correction).
- WebSocket is present in Safari 9.
- Fonts: three locally bundled `@font-face` files (`fonts/Roboto-Regular.woff2`, `fonts/RobotoMono-Regular.woff2`, `fonts/MrsSaintDelafield-Regular.woff2`, each just the Latin subset) instead of plain iOS system fonts — `@font-face` itself has been supported by Safari long before iOS 9, so it's no collision with the ES5/compatibility philosophy. All three families have system-font fallbacks (`"Roboto Mono", "Courier New", monospace`; `"Roboto", "Helvetica Neue", Helvetica, Arial, sans-serif`; and `"Mrs Saint Delafield", "Brush Script MT", cursive` for the `.brand` wordmark) in case the files are ever missing. Deliberately **no** loading from a font CDN at runtime (Google Fonts or similar), because MA setups often run with the iPad having no internet access — the files were downloaded once and live in the repo, exactly like `AppIcon.png`.

### Page router (footer navigation)

The five footer icons (`data-tab="lounge|now|radio|library|search"`, `lounge` leftmost) deliberately carry the same CSS class `tab` that the earlier text-based tabs used, so `switchTab(name, pillName)` and the click wiring in `wireTabs()` could be reused unchanged — only the look comes from a different CSS context via `.footer .tab` (icons instead of text, footer instead of a column).

`TABS` maps each footer name to a pane ID:

```javascript
var TABS = {
  lounge:  { pane: 'pageLounge',    init: loadLoungePage },
  now:     { pane: 'pageNow',       init: syncNowPageState },
  radio:   { pane: 'pageRadio',     init: loadRadioGrid },
  library: { pane: 'pageLibSearch', init: function () { showLibSearchSide('library'); … } },
  search:  { pane: 'pageLibSearch', init: function () { showLibSearchSide('search'); } }
};
```

`library` and `search` share the same pane (`#pageLibSearch`, the two-column layout with compact controls on the left and the list on the right) — only `showLibSearchSide('library'|'search')` switches its `.right` column between `#paneLibrary` and `#paneSearch`. Since two `TABS` keys can point at the same pane ID, `switchTab()` computes visibility once per unique pane ID (instead of blindly overwriting it on every key it processes), otherwise whichever key is processed last would always win.

`enterDetail()`/`navOriginTab`/`popView()` work unchanged from before (see "Development and customization") — detail views technically always run through `switchTab('search', navOriginTab)`, so the originating footer entry (typically "Collection") stays visually active.

The compact playback controls exist **four times** in the DOM: once with the original IDs (`#cover`, `#title`, `#bPlay`, `#vol`, …) inside `#pageLibSearch .left`, once with a `Big` suffix (`#coverBig`, …) inside the full-screen `#pageNow` page, once with a `Radio` suffix (`#coverRadio`, …) inside `#pageRadio .left`, and once with a `Banner` suffix (`#coverBanner`, …) inside `#playbackBanner` (see "Settings" for the Side/Banner choice). So that not every render function has to be written four times, there's the helper family `npEls(base)`/`npText(base, s)`/`npClass(base, cls)`/`npHtml(base, html)`/`npOn(base, evt, handler)` (defined right before `crossfadeCover()`): they iterate over `NP_SUFFIXES = ['', 'Big', 'Banner', 'Radio']` and write the same value to every element set that exists, or wire the same handler to all of them. Each helper silently skips suffixes with no matching element (`$(base + suffix)` then returns `null`) — deliberately relied on: `Banner` intentionally has no Shuffle/Repeat toggles, and `Big` is the only set with standalone heart/add icons instead of the overflow menu (see "NP overflow menu"), without needing any extra JS code anywhere for either. `renderNow()`, `tick()`, `renderVolumeMembers()`, `paintNowHeart()` and every transport/volume click handler use exclusively these helpers, so all existing control sets stay in sync no matter which page is currently visible or whether Side or Banner mode is active. New controls in the Now Playing area should follow the same pattern (add the element to each applicable set, wire it via `npOn()`).

The `.cover`/`.title`/`.btn`/`.toggles`/`.tgl`/`.transport`/`.sub` classes thereby define **four** size tiers over the same set of base classes, purely via descendant selectors: the unchanged base values (medium, historical), `.left .cover { … }` etc. (compact, for `#pageRadio .left` **and** the two-column Library/Search pages — narrow enough that the content on the right gets more room), `#pageNow .cover { … }` etc. (large, for the full-screen view), and `#playbackBanner .cover { … }` etc. (smallest, for the horizontal Banner mode). Since `.left`, `#pageNow` and `#playbackBanner` never hold the same control set at the same time, there are no selector conflicts; new size adjustments should likewise go through the relevant descendant rule, never by changing the base values themselves.

Every volume row (`.vol`, in all four size tiers) carries a small `.nudge` button (`−`/`+`) on each side of the slider for precise single-step adjustment (`VOL_NUDGE_STEP = 1`). The wiring sits right next to the existing slider initialization (an IIFE over `npEls('vol')`) and finds the two `.nudge` elements relative to each slider via `slider.parentNode.getElementsByClassName('nudge')` (index 0 = `−`, index 1 = `+`, matching their order in the markup) — a click sets `slider.value` and fires a synthetic `change` event on the slider itself, instead of duplicating the `volume_set`/`group_volume` command logic. `.left .nudge` gets its own smaller size than the default (see `#playbackBanner`/`#pageNow`) — the 240px-narrow column has less room to spare. `.vol input[type=range] { min-width: 0; … }` also overrides the default `min-width: auto` that form elements otherwise get as flex items: without this rule, the slider refused to shrink below its own content width and, together with the nudge buttons, pushed past the right edge of `.left` instead of sharing the available space with them. The `.lbl` "Vol" label in front of the slider only exists on `Big` (plenty of room on the full-screen page) — the compact `.left` row (Library/Search) has none, the same way Radio already didn't, to save space; both are therefore built identically.

Every page carries a `.page-title` heading at the top: `#pageRadio`/`#pageLibSearch` set it statically or via `showLibSearchSide()` (`#libSearchPageTitle`, "Collection"/"Search" depending on `which`), `#pageNow` sets it dynamically via `renderNowPageTitle(rawTitle, artist, mi)` (called from `renderNow()`) — building "Now Playing" plus an optional ` - {source} - {name}` as a second, dimmed `<span class="pt-dim">`, never via `innerHTML` string interpolation, since title/artist/station name are arbitrary, unfiltered server data. The source is `t('media.radio')` when `mi.media_type === 'radio'`, otherwise the first result of `itemProviderDomains(mi)` through `sourceLabel()` (see "Music source filter"); the name is just the station name for radio, otherwise "{Title} by {Artist}".

Consistent across all four pages: `.page-title` is always its own `flex-shrink: 0` sibling element **outside** the scrollable/padded content area, never a child of it — `#pageLibSearch` and `#pageRadio` both follow the same `.page-title` + `.side-row` structure (`.side-row` is the generic "controls column on the left + content on the right" row, see below; on `#pageRadio` the right column additionally carries the class `.radio-page-body` for `padding`/`overflow-y: auto`), `#pageNow` follows `.page-title` + `.now-content` (which also carries `padding`/`overflow-y: auto`). This keeps the title sitting at the top and left-aligned while scrolling, with the same `border-bottom` divider. `#pageNow .page-title` additionally gets `background: var(--bg-elevated)` (the same surface as the header) — the only page with a `background-image` (the gradient extracted from the cover, see "Now Playing: full screen and gradient") behind it; without its own surface, the title on top would be hard to read or look "obscured by the artwork" depending on the cover's colors.

### Controls position: Side vs. Banner

The compact controls on Radio/Collection/Search (not Now Playing) can be shown either as a left column ("Side", default, the `.left` column in `.side-row` described above) or as a horizontal banner above the footer navigation ("Banner") — switchable via a setting in the gear menu (see "Settings").

- `#playbackBanner` is a genuine flex sibling of `.main-row` and `.footer` inside `.wrap` (not `position: fixed`), with height deliberately `auto` instead of a fixed pixel value. When visible, this makes it push `.footer` down all by itself, and leaves no gap when hidden (`display: none`) — no manual height math is needed, not even for the two responsive variants described below with their different heights. `padding: 14px 16px` (instead of 10px) plus the larger cover/title below give it a noticeably taller row than the first version, so transport, timeline and time display don't feel too cramped.
- Contains the same `Banner`-suffixed elements regardless of screen width (no JS-driven markup swap) — a single `@media (min-width: 680px)` rule decides purely via CSS which of the two variants is visible:
  - **Narrow** (default, e.g. phone width): one row — cover, title+artist, prev/play/next, volume+nudge. No queue/overflow-menu button (no room), the progress bar (`#dialTrackBanner`, wrapped in `.banner-timeline`) runs only as a thin strip along the banner's top edge (`position: absolute; top: 0;`), with no time display.
  - **Wide** (from 680px): `#npQueueBanner` (queue) and `#npMenuBanner` (overflow menu, see "NP overflow menu" below) appear in the row, and `.banner-timeline` instead becomes a normal, centered `.dial` row directly below the transport buttons (`position: static`, smaller than on `.left`/`#pageNow`, but including a time display and the same repeating interval marks as the regular `.dial-track` — see its own `background-image` rule for that inside the `@media` block, just scaled down to the thinner 6px bar). The exact breakpoint number is a rough guess ("no longer phone width") that hasn't been verified on a device from here.
  - The progress bar stays tappable in both variants via the same generic `npEls('dialTrack')` click wiring as the other dial tracks.
  - **Time display deliberately different from everywhere else**: `#tRemainBanner` shows the remaining time (`-m:ss`) instead of elapsed time, `#tDurBanner` shows the total length. Since `npText('tPos', …)` (see `tick()`) writes the same elapsed time into every suffix, a plain `tPosBanner` offshoot would automatically have shown elapsed instead of remaining time — `#tRemainBanner` therefore deliberately sits outside that sweep, and `tick()` computes and writes it directly (`dur - pos`) instead of going through `npText()`.
  - **Layout**: `.banner-row` splits into `.banner-left` (cover+title), `.banner-center` (transport, with `.banner-timeline` directly below it in the same flex-column container) and `.banner-right` (queue/menu/volume) — the classic three-part technique for true centering without CSS Grid: `.banner-left`/`.banner-right` both grow from a zero basis (`flex: 1 1 0`), so whatever space is left over after `.banner-center`'s own width is split evenly between them, keeping `.banner-center` exactly centered no matter how much space the cover/title on the left or the volume/icons on the right need.
  - **Cover/title bigger than in the first version** (58px cover instead of 46px, 17px title font instead of 14px, `.banner-titles` 220px wide instead of 200px) — more presence for artwork/song name, matching the taller banner row overall.
  - **Title links to the album**: since there's no room for its own `.sub.album` line in the banner (unlike `.left`/`Big`/`Radio`), `#titleBanner` takes on that role itself — `wireNowNav(mi)` (see "Now Playing: full screen and gradient" for the rest of the function) makes it tappable (`.title.tap`) and calls `enterDetail(); openAlbum(mi.album);` whenever an album with `item_id` is present, exactly like `.sub.album.tap` does on the other size tiers.
  - **Transport/volume deliberately more compact** than the rest of the banner: `.btn`/`.btn.big` 28px/34px (instead of 34px/42px), `.vol` `max-width: 170px` (instead of 280px), `.nudge` 18px — makes room for the bigger cover/title on the left without making the banner wider overall.
  - **Marquee scroll for titles/artists that don't fit**: the only size tier without `overflow`/`text-overflow: ellipsis` directly on `.title`/`.sub` — clipping is instead handled by the `.banner-titles` wrapper (`overflow: hidden`, fixed width), while `.title`/`.sub` themselves get `white-space: nowrap; display: inline-block;`, letting them become wider than the wrapper. `refreshBannerMarquee()`/`marqueeFor()` (NOW PLAYING section, called from `renderNow()` and `applyControlsPosition()`) measure `scrollWidth` against the wrapper's width; if the text exceeds it by more than 4px, the CSS custom property `--marquee-dist` (a negative pixel distance) is set and the `.marquee` class is added, animated via `@keyframes marqueeScroll` (hold → scroll left → hold → scroll back, an 8s cycle). No nested inner span needed, since `.title`/`.sub` are transformed directly.
- `applyControlsPosition()` (SETTINGS section) decides on every `switchTab()` call whether the banner should actually be visible (banner mode **and** `currentTab` ∈ {`radio`, `library`, `search`} — never on `now`), toggling `#playbackBanner`'s `display` as well as a `hide-side` class on every `.side-row` element (`.side-row.hide-side .left { display: none; }`).
- `#queuePanel` needs no special handling for the banner case anymore (see "Queue: shared panel that shifts the content") — it sits inside `.main-row` (as a flex sibling of `.pages`), but `.main-row` itself, being a `flex: 1` element, always automatically fills the space between `.top` and `#playbackBanner`/`.footer` regardless of whether or how tall the banner currently is — so `#queuePanel`'s height adjusts automatically too, with no pixel math involved.

### NP overflow menu

The compact (`.left`), Radio, and (in its wide state) Banner controls replace `Big`'s standalone heart/add icons with a single "⋮" button (`#npMenu`/`#npMenuRadio`/`#npMenuBanner`) that opens a small popover with the same actions — plus "View metadata" on Banner — to save space. `Big` keeps its standalone icons (plenty of room on the full-screen page), so no `npMenu*`/`npFavRow*`/`npPlaylistRow*`/`npInfoRow*` elements exist there.

- Each popover panel (`.np-menu-panel`) sits nested directly **inside** its trigger button (the trigger carries `position: relative`), rather than being positioned separately in the document — this makes it anchor correctly automatically wherever the button ends up on a given size tier, without a position override per tier. `.np-menu-panel` opens downward by default (plenty of room below the title row on `.left`/Radio); `.np-menu-panel.up` (Banner) opens upward instead, since the banner sits right above the footer.
- `NP_MENU_SUFFIXES = ['', 'Radio', 'Banner']` plus `npMenuOpenSuffix` (a single variable rather than one per suffix): since only one of the three triggers is ever visible at a time (their pages/modes are mutually exclusive — see `switchTab()`/`applyControlsPosition()`), a single "which menu is currently open" state is enough. `toggleNpMenu(suffix)`/`closeNpMenu()` plus a dedicated `document.addEventListener('click', …)` listener (click-outside closes, same pattern as the queue panel) manage this.
- The rows themselves are again wired through the generic `npEls`/`npOn` family: `npFavRow`/`npPlaylistRow`/`npInfoRow` (the last one only exists on Banner). `npFavRow` is kept up to date by `paintNowHeart()` (the same favorite state, just as a text row instead of an icon: "♥ Remove favorite"/"♡ Add to favorites"), `npPlaylistRow`/`npInfoRow` call the same `openPlaylistSheet()`/`openMetadataSheet()` logic as the corresponding action-sheet entries.
- **Queue button everywhere**: `#npQueue`/`#npQueueRadio`/`#npQueueBanner` (the last one only in the wide Banner state, see above) join the already-existing `#npQueueBig` — all four are now just further `npEls('npQueue')` hits, and `paintQueueToggle()`/the click wiring in "Queue: shared panel that shifts the content" were generalized accordingly (no more hardcoded id array for the Now Playing page).

## Configuration

Credentials and device-specific settings live in the separate file `ma-env.js`. It's loaded by `ma-dashboard.html` via `<script src="ma-env.js">` and excluded via `.gitignore`. `ma-env.example.js` serves as the template.

```javascript
var CFG = {
  MA: 'http://192.168.1.5:8095',   // MA base URL, no trailing /
  TOKEN: '<long-lived-token>',     // MA: Settings > User > Token
  PLAYERS: [],                     // optional whitelist of player_ids
  DEFAULT_PLAYER: '',              // player_id that should be active at startup; empty = automatically the currently playing player/group, otherwise the first one
  SEARCH_LIMIT: 12,                // hits per category
  LIST_LIMIT: 200,                 // tracks/albums per detail view
  IMG_COVER: 512,                  // cover edge length via imageproxy
  IMG_THUMB: 160                   // thumbnail edge length via imageproxy
};
```

If `ma-env.js` or individual values are missing, fallback defaults in the main script kick in. If `CFG.MA` is empty, the current `location.host` is used (e.g. when MA serves the file itself).

## Important WebSocket commands

### Player

- `players/all` — list all players.
- `players/cmd/play_pause` — toggle play/pause.
- `players/cmd/next`, `players/cmd/previous` — change track.
- `players/cmd/seek` — set the position within the current track.
- `players/cmd/volume_set`, `players/cmd/group_volume` — volume; for sync groups `volume_level` is null, use `group_volume` instead.
- For individual members of a group player, `players/cmd/volume_set` is sent with that member's own `player_id`.
- `players/cmd/group` — add a player to a group (parameters: `player_id` of the player being added, `target_player` as the group leader).
- `players/cmd/ungroup` — remove a player from any sync/group membership (parameter: `player_id`).
- Whether a player can be grouped at all is shown by the `set_members` feature flag in `supported_features`.

### Queue

- `player_queues/all` — load all queues.
- `player_queues/get_active_queue` — a player's active queue.
- `player_queues/items` — a queue's contents.
- `player_queues/play_media` — play a medium (`option: 'replace'|'next'|'add'`).
- `player_queues/play_index` — jump to a specific queue entry.
- `player_queues/shuffle`, `player_queues/repeat` — control shuffle/repeat.
- `player_queues/clear`, `player_queues/delete_item` — clear the queue / remove an entry.
- `player_queues/play_media` with `radio_mode: true` — start radio mode, seeding it from the given `media` (see "Radio Mode"); `player_queues/dont_stop_the_music` (parameters: `queue_id`, `dont_stop_the_music_enabled`) is reused as a best-effort way to ask the server to stop auto-extending when radio mode turns off.
- When `shuffle_enabled` or `radio_mode` is active, the queue shows a hint banner that tracks are being shuffled or generated dynamically.
- The display only shows the last `QUEUE_HISTORY_LIMIT` (3) already-played tracks before the current one, not the complete history — this only affects the rendering in `loadQueue()`; the server-side queue is unaffected.
- On a plain track change, the list isn't rebuilt but updated via a slide animation instead (see "Cover crossfade and queue slide").

### Media

- `music/search` — global search.
- `music/item_by_uri` — resolve a medium by its URI (returns the library item with its `favorite` flag).
- `music/artists/artist_albums`, `music/artists/artist_tracks` — artist detail view: full discography and full track list respectively.
- `music/artists/top_tracks` — an artist's real top/featured tracks (aggregated/deduplicated across providers for library items); not to be confused with `artist_tracks`, which returns the complete track list.
- `music/albums/album_tracks` — album detail view.
- `music/playlists/playlist_tracks` — playlist detail view.
- `music/podcasts/podcast_episodes` — podcast detail view.
- `music/<type>s/library_items` — list saved entries of a media type (`type` = `playlists`, `artists`, `albums`, `tracks`, `radios`, `podcasts`, `audiobooks`).
- `music/playlists/create_playlist` — create a playlist (parameter: `name`).
- `music/playlists/add_playlist_tracks` — add tracks to a playlist (parameters: `db_playlist_id`, `uris`).
- `music/favorites/add_item` — add a favorite (parameter: `item: uri`).
- `music/favorites/remove_item` — remove a favorite (parameters: `media_type`, `library_item_id`).
- `music/recommendations` — **not verified against a live server from here** (see "Lounge (home page)"); used for the Lounge page's non-provider-specific "Recommended" section, a plausible command name given the other `music/*` commands above, but its exact existence/response shape hasn't been confirmed.

### Player configuration

- `config/players/get_value` — read a config value (parameters: `player_id`, `key`).
- `config/players/save` — write config values (parameters: `player_id`, `values`).

## Progress bar and the beta bug

In current MA beta versions (from commit `cadcd96fd` onward), the server no longer sends continuous position ticks. Instead it only delivers anchor pairs:

- `elapsed_time` — position within the track, in seconds.
- `elapsed_time_last_updated` — the server's Unix time for this anchor.

Anyone who only redraws the bar on every event sees a static bar that only jumps on pause/seek/track-change — exactly the old HA version's behavior.

The correct implementation in the dashboard:

1. Remember the anchor (`anchorPos`, `anchorAt`).
2. During playback, interpolate locally: `pos = anchorPos + (serverNow() - anchorAt)`.
3. Call `tick()` every 500ms to update the bar smoothly.
4. Correct the clock against the MA server via the HTTP `Date` header from `/info`, so an iPad with the wrong time doesn't shift the bar.

## Cover crossfade and queue slide

A hard `innerHTML` swap on every track change feels jarring (the cover flashes, the queue visibly rebuilds). Both are instead handled as a soft transition animation, purely with CSS transitions (no framework, ES5/iPad-friendly):

- **Cover** (`renderNow()` → `crossfadeCover()`): a new `<img>` or placeholder element is layered over the existing one (`.cover img`/`.cover .ph` are `position: absolute` inside the `position: relative` container `.cover`) and faded in via an `opacity` transition (the `.show` class). The old element is only removed from the DOM after the transition finishes (`setTimeout`, 420ms).
- **Queue** (`loadQueue()` → `tryQueueSlide()`): on every refresh, it's checked whether only the visible window has shifted since the last render (`lastQueueIds`/`lastQueueStartIdx`) — i.e. the order and count of queue items are identical, only the current track has advanced (the normal case while playback continues). In that case nothing is rebuilt: the `.now` marker moves to the matching row, and the rows falling out of the window at the top slide away via a height/opacity transition (`slideRowAway()`, class `.row.q-leave`) instead of being removed outright. For real changes (shuffle, add/remove, player switch — `lastQueueIds` no longer matches), the full rebuild via `renderQueueRows()` still applies. The "Loading …" hint now only appears when the list is currently empty (`box.getElementsByClassName('row').length === 0`), not on every silent background refresh.
- Both mechanisms use the generic class helpers `hasClass()`/`addClass()`/`removeClass()` (string-based, no `classList`, consistent with the rest of the file's ES5 style).

## Now Playing: full screen and gradient

The Now Playing page (`#pageNow`) is centered and full-screen; its CSS classes (`.cover`, `.titlerow`, `.transport`, `.tgl`, `.vol`, …) are identical to the compact controls, just enlarged via `#pageNow` descendant rules (e.g. `#pageNow .cover { width: 320px; … }`) — one single source of truth for how each control looks, see "Page router (footer navigation)".

When a new cover loads, `updateNowGradient(url)` also tries to extract a soft gradient **and** a live `--accent` color from the artwork: a **separate** `Image` object (`crossOrigin = 'anonymous'`) loads the same URL again, draws it onto a small offscreen `<canvas>` (12×12) and reads all the pixels at once via `getImageData` — two sample pixels produce a two-color `linear-gradient(...)` at reduced opacity as the `#pageNow` background (layered over the flat `--bg` surface, staying legible in both themes that way), and `pickAccentFromImageData()` picks the "most vivid" one from those same 144 pixels (saturation, weighted toward mid brightness rather than a plain average, which tends to skew grayish) as the accent color — the gradient is always computed, but `applyTrackAccent()` only actually applies the color as `--accent` when the "Dynamic" swatch is active in settings (see "Accent color"); otherwise the chosen preset stays untouched. Deliberately a second `Image` object instead of the one shown in the cover: if the MA server doesn't send matching CORS headers on `/imageproxy` responses, the canvas stays "tainted" and `getImageData()` throws a `SecurityError` — caught via `try/catch` in `updateNowGradient()` (fallback: a flat `--bg` background plus `applyTrackAccent(null)`, see "Accent color"), **without** affecting the actual cover display (which still runs through the first, untouched `Image` object). Both are therefore deliberately best-effort, not a hard requirement.

## Radio

The Radio page (`#pageRadio` → `#radioGrid`, populated by `loadRadioGrid()`) shows only **favorited** radio stations (`music/radios/library_items`, filtered client-side to `favorite === true`) as a tile grid (`.radio-tile`), grouped by country.

- The grouping is **best effort**: `radioCountry(it)` first checks `RADIO_COUNTRY_OVERRIDES` — a manually maintained mapping from exact station name to country, for stations whose provider supplies no country metadata at all (currently including "2SER 107.3", "ABC Jazz HLS", "TrustFM", "FBi Radio - Sydney - 94.5 FM (MP3)" → "Australia") — and otherwise reads `it.metadata.country` or `it.country` if present. MA doesn't guarantee a country field for every radio provider — stations with no usable value (and not in the manual list either) land together in a trailing "Other" group instead of the grouping breaking down entirely. New stations without a country: just add another entry to `RADIO_COUNTRY_OVERRIDES`.
- Every tile (`radioTile()`) uses the station's artwork (`imgUrl(it, CFG.IMG_THUMB)`) as a `background-image` with a dark gradient overlay (`.rt-shade`) for name legibility; without artwork, a simple note-glyph placeholder (`.rt-ph`), consistent with the app's other placeholder pattern.
- Tapping (`playRadioStation()`) plays the station via `player_queues/play_media` (`option: 'replace'`) on the active queue and then switches to the Now Playing page via `switchTab('now')`.
- The footer icon (`svgIcon('radio')`) deliberately shows an old-fashioned radio set (body, antenna, round speaker, tuning knob, dial bar) instead of a generic broadcast-wave symbol.

## Music source filter

In Library and Search, the results list can additionally be filtered by streaming source (Tidal, YouTube Music, SoundCloud, …), via a chip row (`#libSourceFilters` or `#sourceFilters`, populated by `renderSourceFilters()`) in its own section set off by a thin divider and a "Source" label (`.filter-section`/`.filter-label`, see below) — the same way the media-type filter chips (label "Filter", `#filters`/`#libFilters`) and the sort chips (label "Sort", `#sortFilters`/`#libSortFilters`) each get their own section, rather than all being mixed into one row like before. The queue isn't a `LIB_TYPES` entry and therefore has no `currentLibType` mode of its own that would need to hide these sections — it lives exclusively in the shared `#queuePanel` (see "Queue: shared panel that shifts the content").

- The chip list itself does **not** come from the currently loaded results, but from `availableSourceDomains` — a list of the music providers actually configured on the server, loaded at startup via `refreshAvailableSources()` (called from `bootstrap()`, alongside `players/all`/`player_queues/all`, as soon as WebSocket authentication has gone through) through `loadMusicSources()` (`config/providers`, `provider_type: 'music'`, see also "Settings"). This means the chips are already visible before a search has even been started or the library opened for the first time, and they stay stable (they don't disappear just because a filter currently has no hits).
- `itemProviderDomains(it)` returns a single item's actual provider domains for the **filtering itself** (not for the chip list): it prefers `it.provider_mappings[].provider_domain` (deduplicated), since library items only carry `provider === 'library'` at the top level (see "Library items and provider resolution") and the real source only shows up in `provider_mappings`; falls back to `it.provider` if that isn't the pseudo-provider `library` (the typical case for search results, which usually already resolve to a real provider domain).
- `sourceLabel(domain)` translates known domains into friendlier names (`SOURCE_LABELS`, e.g. `ytmusic` → "YouTube Music"), with a title-case fallback for unknown domains.
- The filtering itself happens purely client-side on the already-loaded array (`itemMatchesSource()`); it involves no extra server request.
- Deliberately only on the respective top-level results list (library chips or search-result groups), not in the detail tabs of an artist/album/playlist view.

## View metadata

At the very bottom of the action sheet (`#sheetbg`), right above "Cancel", sits an additional "View metadata" button (`#aMetadata`, always visible, with none of the conditional `.gone` logic that "Open"/"Artist"/"Album" have). It opens its own sheet (`#metadataSheetbg`, `openMetadataSheet(it)`) that re-fetches the item from the server via `resolveItem(it.uri, …)` (the same resolution used for favorites, see "Favorite asymmetry") and shows the result as fully indented JSON (`JSON.stringify(data, null, 2)`) inside a `<pre class="meta-json">` — deliberately generic instead of a curated field-by-field view, since the set of fields varies a lot by media type and provider. Runs, like `refreshNowFav()`, through the same race guard (`metadataSheetUri`, discarding the response if the sheet has since been closed or reopened for a different item). Without `it.uri` (should practically never happen), the client-side object already at hand is shown directly, with no server call.

## Gently Play Now

Right below "Play now" (`#aNow`) in the action sheet (`#sheetbg`) sits an extra "Gently play now" button (`#aGently`) as a gentler variant: instead of switching hard, it fades the active player down to 0% volume over 3 seconds, only then switches the queue, and afterward fades back up to the previous volume over 3 seconds.

- The actual `player_queues/play_media` request (including the `startFrom` logic for album/playlist context) is built by both `playPending()` **and** `#aGently` through the shared helper `buildPlayPendingArgs(option)`, rather than duplicating it — `playPending(option)` calls it and sends right away; `#aGently` calls it, remembers the current volume beforehand (`activePlayer().volume_level` or `.group_volume` as a fallback), and only sends after the fade-out.
- The fades run through the same `fadeVolume(ids, target, durationMs, cb)` helper as the Quick Actions "Play Music"/"Sleep" (see "Quick Actions") — no separate ramp logic.
- If the `play_media` call fails after the fade-out, the volume still fades straight back up to its original value (otherwise the player would be left silent after an error).

## Radio Mode

An icon button (`#bQueueRadio`, radio-tower SVG via `svgIcon('radiotower')`) in the queue panel's toolbar, next to Refresh/Clear (`#queueToolbar`) — not in the `.toggles` row like the "Don't Stop the Music" button it replaced. Seeds MA's actual "Start Radio" feature from whatever's currently playing, so the queue gets continuously extended with similar tracks (`q.radio_mode` on the PlayerQueue object, already read elsewhere for the `queue.radioBanner` hint).

- **Not verified against a live server from here**, unlike `player_queues/dont_stop_the_music` below (which was corrected once already based on a real error message): `startRadioMode()` sends `player_queues/play_media` with `radio_mode: true` alongside the seed track's `media` and `option: 'replace'` — based on general familiarity with MA's API shape, not a confirmed response. If the server rejects or ignores it, check the actual "Start Radio" request shape a current MA release's own web UI sends and adjust `startRadioMode()`. `radioSeedUri()` prefers the active queue's `current_item.media_item.uri`, falling back to the player's raw `current_media.uri` for sources with no queue-tracked item (e.g. a foreign AirPlay/Spotify Connect stream).
- `option: 'replace'` is deliberate: matches how "Start Radio" works elsewhere (Spotify, MA's own web UI) — the seed becomes track 1 of a fresh, continuously-extending queue rather than being appended after whatever was already queued. The seed briefly restarts as an accepted side effect.
- **Turning it off** (`stopRadioMode()`) has no confirmed dedicated command either. It reuses `player_queues/dont_stop_the_music` (parameters `queue_id` + `dont_stop_the_music_enabled: false` — **not** a generic `enabled`, which failed on the first attempt with `"dont_stop_the_music_enabled of type <class 'bool'> is required"`; this command and its state field *are* confirmed against a real server response) as a best-effort "please stop auto-extending" signal, fired and forgotten — the local cleanup below runs regardless of whether the server actually honors it.
- `radioModeOn`/`radioBaselineIds` (global variables) are read by `loadRadioModeState()` from `q.radio_mode` — called from the same places `player_updated`/`queue_updated` handling already touches (`selectPlayer()` and the `handleEvent()` branch for `queue_updated`/`queue_added`), so the button also picks up radio mode being started/stopped from another client.
- **Cleans up its own additions when it turns off, and tags them while it's on**: MA exposes no "added by radio mode" flag on individual queue items, so this is a best-effort heuristic rather than a precise one. Whenever `q.radio_mode` turns on, `snapshotRadioBaseline()` takes a snapshot of the current queue's item ids into `radioBaselineIds`. While radio mode is on, `queueRow()` renders a small tag icon (`.q-radio-tag`, the same `radiotower` glyph, `queue.radioTagTitle` tooltip) next to the track name of every row whose id isn't in that snapshot. When `q.radio_mode` turns back off, `loadRadioModeState()`'s on→off transition calls `cleanupRadioAdditions()`, which deletes every upcoming queue item (i.e. after the currently playing one) whose id isn't in the baseline, via `player_queues/delete_item`, and shows a toast with the removed count. It never touches the currently playing item or anything already played (before it in the list). A track the user manually queues while radio mode is still on would get tagged/swept up the same way, since there's no real per-item source flag to tell the two apart from the client — an accepted limitation of the heuristic.

## Quick Actions

The `#stationMenu` dropdown (opened via the `#stationMore` button next to the station bar, which carries the visible text "Quick Actions ❯") carries, below the player list, an additional "Quick Actions" heading and a row of two square buttons (`.qa-row` / `.qa-btn`): `#qaPlayMusic`/`#qaSleep`. The identical pair also lives on the Lounge home page (`#qaPlayMusicLounge`/`#qaSleepLounge`, see "Lounge (home page)") — both button sets call the same shared `doPlayMusic()`/`doSleep()` functions rather than duplicating the logic; only the dropdown's own pair additionally calls `closeStationMenu()` first, since the Lounge page isn't a dropdown that needs closing.

- **Play Music** (`doPlayMusic()`): resumes the active player (`players/cmd/play_pause`, only if not already `isPlayerPlaying()`) and fades its volume up to 50% over 3 seconds. MA has no dedicated "play the last track" command; since the queue stays at its last position after pause/stop, a plain resume is the closest available implementation of "play what was last playing".
- **Sleep** (`doSleep()`): fades **all** known players (`playerIds`) down to 0% volume in parallel over 5 seconds, then pauses whichever of them were still playing at that point.
- Both use the shared `fadeVolume(ids, target, durationMs, cb)` helper: ramps linearly via `setInterval` (every 150ms) using `players/cmd/volume_set` or `players/cmd/group_volume` (the same switching rule as the normal volume slider — `volume_level === null` means a group player), calling `cb` once the duration has elapsed. The same helper also drives "Gently play now" in the action sheet (see above) — no separate fade mechanism.

## Lounge (home page)

The leftmost footer tab (`#pageLounge`, `pagetitle.lounge`/`tab.lounge` = "Lounge", `svgIcon('lounge')` a simple side-view sofa silhouette) — a "home" page combining the Quick Actions buttons (see above) with four best-effort "what to play" sections (`LOUNGE_SECTIONS`, rendered into `#loungeSections`), a type filter + a source filter (`#loungeTypeFilters`/`#loungeSourceFilters` — no "sort", see below), and pull-to-refresh. `TABS.lounge.init` calls `loadLoungePage(false)`; a plain tab switch back to Lounge therefore does **not** refetch or rebuild anything (see "Scroll position is preserved by never rebuilding" below) — only the very first visit, or an explicit pull-to-refresh (`force=true`), actually reloads data.

- **Four categories, each broken into one horizontally-scrollable rack of cards per provider** (`.rack-scroll`/`.rack-card`, modeled on the Radio page's `.radio-tile`) instead of the vertical `.list`/`mediaRow()` rows used elsewhere in the app — "Recently Played", "Recently Added Albums", "Recently Added & Favorite Tracks", then "Recommended" (MA's own suggestions, kept as its own, separate category rather than merged into "Recently Played" — see below). Each category is **not** one mixed rack of cards from every provider — it's a list of **subsections**, one full rack per provider, titled e.g. "Recently Added Albums - Tidal" and "Recently Added Albums - YouTube Music" as two separate sections stacked vertically (`loungeData[key]` is this list of `{ title, domain, items }` subsections, built by `groupLoungeItemsByProvider()` for the first three categories — see below for how "Recommended" differs). `rackCard(it, type, opts)` builds one card (artwork, name, artist only — no provider text on the card itself, since the subsection heading above it already states the provider); `renderRack(cards)` wraps one subsection's cards in a `.rack-scroll` container. Scrolling is deliberately plain native `overflow-x: auto` + `-webkit-overflow-scrolling: touch` plus CSS `scroll-snap-type`/`scroll-snap-align` for the "flipping through records" feel — no JS-driven momentum or animation loop, so it stays light on an old iPad (both are handled entirely by the browser's own compositor).
- **Each category renders into its own stable container, never a shared one** (`ensureLoungeCategoryContainers()` builds one empty `#loungeCat-<key>` div per category inside `#loungeSections`, created exactly once; `renderLoungeCategory(key)` is the only thing that ever replaces one of those containers' contents, and only for that one key). `loadLoungePage(force)` shows every category's own "Loading…" hint immediately (`renderLoungeCategory()` called once per key up front) and then re-renders *only* the one category whose own `music/*` call just completed, as its own callback (`loadLoungeAlbums(function () { renderLoungeCategory('albums'); })`, etc.) — not a single shared callback that rebuilds the whole page. An earlier version used one shared `renderLoungeSections()` as the callback for all three requests, wiping and rebuilding *all four* categories (every subsection, every card, every wheel listener) up to three extra times after the first paint as each response landed, each time reshuffling the whole page's layout under whatever the user was doing — the likely cause of the page feeling like it "freezes"/gets stuck scrolling for the first few seconds on Lounge. Splitting into per-category containers both fixes that churn and gives a real, category-scoped "still loading" indicator rather than one global one.
- **Desktop sideways scrolling through three independent mechanisms, none of which may block vertical page scroll**: (1) a genuine trackpad horizontal swipe arrives as a `deltaX`-dominant `wheel` event, which plain `overflow-x: auto` already scrolls natively with no JS at all; (2) `wireRackWheelScroll()` (wired onto every rack from `renderRack()`) converts a plain *vertical*-only mouse wheel into horizontal `scrollLeft` movement whenever `deltaY` is dominant, so a regular desktop mouse with no trackpad/shift can scroll a rack sideways too; (3) `wireRackDragScroll()` + the single shared `wireLoungeDragScrollGlobal()` listener pair add click-and-drag panning as a fully independent fallback that works regardless of wheel/trackpad quirks (drag state - `loungeDragScroller`/`loungeDragStartX`/`loungeDragStartScroll`/`loungeDragMoved` - lives in a few module-level variables read by one shared `document`-level `mousemove`/`mouseup` pair rather than per-rack listeners, so it stays cheap no matter how many racks exist; `loungeDragMoved` suppresses the dragged-over card's click via a capture-phase listener on the scroller, so a drag never also "opens" whatever card it passed over; `.rack-scroll` gets a `cursor: grab`/`grabbing` affordance for this). Mechanism (2) is deliberately **bounded**: it only calls `preventDefault()` while the rack actually still has room to move further in the wheeled direction (checked via `scrollLeft`/`scrollWidth`/`clientWidth` on every event) — once a rack is scrolled all the way to either end, **or has no horizontal overflow at all**, the handler does nothing and lets the event propagate up to `#loungeBody` so the page keeps scrolling vertically. An earlier version of (2) called `preventDefault()` unconditionally on every dominant-vertical wheel tick over *any* rack; since the Lounge page is now mostly racks, that silently swallowed the mouse wheel almost everywhere on the page — the cursor only had to be hovering a rack (scrollable or not) for a normal vertical scroll gesture to do nothing at all, which was the actual "page freezes/stuck scrolling" bug.
- **"Recently Played" is a client-side playback log, not a server query** (`recordRecentlyPlayed()`, hooked into `renderNow()`'s existing `uri !== npUri` track-change detection; `loadLoungeRecentSection()` groups the log into one subsection per provider, e.g. "Recently Played - Tidal"): the earlier version built this from `music/<type>s/library_items` filtered to a `last_played` timestamp, which turned out inaccurate for two reasons — the fetch is capped at `CFG.LIST_LIMIT` with no guaranteed recency order from the server, and it fundamentally only covers items actually saved to the library, missing anything played via search/radio without being favorited/added. The new approach instead just records whatever the app itself observes playing (uri, name, artist, media_type, provider domain, the resolved `media_item` snapshot if the queue gave us one, and the cover URL `renderNow()` already resolved as a fallback), deduplicated by uri (a replay moves the entry to the front instead of duplicating it), capped at `RECENTLY_PLAYED_LIMIT` (30) and persisted to `localStorage` (`RECENTLY_PLAYED_KEY`) so an always-on kiosk display accumulates real history across reloads. 100% accurate for anything actually played through this app and provider-agnostic by construction, and needs no new/unverified MA command. Starts empty on a fresh install or after clearing site data — an accepted tradeoff. Deliberately **separate** from "Recommended" (MA's own `music/recommendations` suggestions) rather than folded into it, per the distinction the user drew between "what was actually played" and "what MA suggests".
- **"Recently Added Albums"** (`loadLoungeAlbums()`) and **"Recently Added & Favorite Tracks"** (`loadLoungeTracks()`): straightforward `music/albums/library_items`/`music/tracks/library_items` calls, sorted client-side by `timestamp_added` descending and capped to `LOUNGE_SECTION_LIMIT` (20), then split into per-provider subsections by `groupLoungeItemsByProvider()`. The tracks category additionally unions in any favorited track not already in that top-20 (capped at double the limit overall) before grouping, so a track that's favorited but wasn't recently added still shows up, without requiring a separate "favorites" rack.
- **"Recommended"** (`loadLoungeRecommended()`): MA's own cross-provider recommendation engine, **still not verified against a live server from here** — `music/recommendations` is a plausible command name given this project's other `music/*` commands, but the exact command and its response shape (a flat item list? folders already grouped by provider? something else?) haven't been confirmed. Parsed defensively: an array of folder-like objects (each carrying its own `.items`) is rendered as one subsection per folder; a flat array of media items is treated as a single unnamed folder instead. **Unlike** the two "Recently Added" categories above, these subsections come straight from MA's own folder structure rather than being re-grouped purely by provider here — each folder is already a curated, named grouping (e.g. "More of What You Like", "The Hits") and splitting that apart would lose the curation. Instead, the provider is simply appended to the existing folder name in parentheses: `"More of What You Like (SoundCloud)"`, `"The Hits (Tidal)"` (`folder.provider_domain`, falling back to the first item's own `itemProviderDomains()` if the folder itself didn't carry one; no suffix at all if neither resolves). If the server rejects the command or the shape doesn't match, `loungeStatus.recommended` becomes `'error'` and the category shows a quiet error hint instead of breaking the rest of the Lounge page — check the actual command/response shape a current MA release's own web UI uses and adjust `loadLoungeRecommended()` if wrong.
- **Generic provider-generated playlists are filtered out of "Recommended"** (`isGenericGeneratedPlaylist(it)`/`isGenericFolderName(name)`, `GENERIC_PLAYLIST_KEYWORDS`): MA doesn't expose a reliable "this is an auto-generated shell, not a real playlist" flag this project has found, so this is a best-effort, name-based heuristic instead — it skips any playlist (or recommendation folder) whose name contains a known generated-playlist pattern (`"daily mix"`, `"discover weekly"`, `"release radar"`, `"made for you"`, …) or ends in `"radio"` (Spotify/YouTube Music-style seeded-radio shells like "Artist Radio"). Expect to extend the keyword list once it's clear what an actual provider combination returns.
- **Two independent filters, no "sort"** — both operate on whole subsections, never on individual cards (`renderLoungeFilters()`, same `.filt` chip pattern `buildLibFilters()` uses for the Collection page):
  - **Type filter** (`#loungeTypeFilters`, `loungeFilter`): "All" or one of the four category headings — shows only the matching category, hiding every subsection under the others as a unit. Wired cheaply: a click just calls `applyLoungeFilterVisibility()` (toggles each category container's `display`; no data touched, nothing rebuilt).
  - **Source filter** (`#loungeSourceFilters`, `loungeSourceFilter`): "All" + one chip per actually-configured provider domain, via the exact same `renderSourceFilters(boxId, domains, current, onPick)`/`availableSourceDomains` helper the Library/Search source chips already use (`onPickLoungeSource()`; `refreshAvailableSources()` keeps all three chip rows — Search, Library, Lounge — in sync from one `config/providers` call). Shows only the subsections whose own `domain` matches the chosen provider across *every* visible category; if a category has data but none of it matches, `renderLoungeCategory()` shows a dedicated `lounge.sourceEmpty` hint instead of the category's normal empty-state text. Since this actually changes which subsections exist per category, a click calls `renderAllLoungeCategories()` (every category's DOM is rebuilt) rather than just toggling visibility.
  - There used to be a second "Recent"/"Provider" **sort** chip pair here that re-ordered subsections alphabetically by provider; it was replaced by the Source filter above per feedback that provider should be a filter, not a sort.
- **Pull-to-refresh** (`wireLoungePullToRefresh()`, `#loungePullHint`): touch-only gesture detection on `#loungeBody` — when a touch starts with `scrollTop <= 0`, the drag distance is tracked and faded into `#loungePullHint`'s opacity; releasing past `PULL_THRESHOLD` (70px) calls `refreshLoungeData()` (`loadLoungePage(true)`). Deliberately never calls `preventDefault()` or transforms the scroller itself, so it never fights the browser's native scroll/rubber-banding — purely observational, cheap per-`touchmove` work (a few comparisons and one style write), consistent with the "light rendering, no lag on an old iPad" constraint. Re-querying the same already-used `music/<type>s/library_items`/`music/recommendations` commands on demand is a normal, low-cost, idempotent operation — nothing elsewhere in this app treats them as rate-limited — so a manual refresh gesture is a reasonable fit for the MA API.
- **Scroll position is preserved by never rebuilding on a plain return visit**: the previous version's `TABS.lounge.init` called `loadLoungePage()` unconditionally, which cleared and rebuilt `#loungeRecent`/`#loungeRecommended` every single time the Lounge tab became active again — including when "Back" from an album/playlist opened from Lounge returns there via `popView()`'s `switchTab(origin)` fallback. Clearing a scrolled container's children collapses its content height and clamps the scrollable ancestor's `scrollTop` to 0, and the clamp doesn't undo itself once content is added back — so every return trip landed back at the top of the page regardless of where the user had scrolled to. `loadLoungePage(force)` now only does that fetch-and-rebuild work on the very first visit (`loungeLoaded` still `false`) or when `force` is `true` (pull-to-refresh); a plain revisit is a no-op, so `#loungeBody`'s DOM — and therefore its `scrollTop` — is simply never touched.
- `#pageLounge .menu-head` gets its own scoped CSS rule (font/color/letter-spacing), the same way `.station-menu .menu-head`/`.group-menu .menu-head` already do, rather than making the shared base `.menu-head` class unscoped — plain `.menu-head` elsewhere (e.g. inside `#settingsMenu`/`#accentMenu`) isn't reliably styled either, a pre-existing inconsistency not worth fixing just to make this page render correctly.
- **Quick Actions row is width-capped** (`.lounge-qa-section .qa-row { max-width: 320px; }`): the shared `.qa-btn`/`.qa-row` CSS (see "Quick Actions") uses `flex: 1` so the two buttons split whatever width `.qa-row` has — fine in the narrow `#stationMenu` dropdown, but on the Lounge page's full-width body that stretched each button into an oversized, sparsely-padded rectangle. Capping the row's own width instead of the buttons keeps both a reasonable, evenly-spaced size.

## Queue: shared panel that shifts the content

The queue is neither its own footer entry nor a library chip, but a **single shared panel** (`#queuePanel`) that pushes `.pages` aside when opened instead of laying itself over it. Triggers: the suffixed `#npQueue`/`#npQueueBig`/`#npQueueRadio`/`#npQueueBanner` icons (title row or banner row of the respective size tier, see "Page router (footer navigation)") — simply further `npEls('npQueue')` hits, wired in one go via `npOn('npQueue', 'onclick', toggleQueuePanel)`. There used to also be a separate `#libQueueToggle` button at the top of the Collection page; it was removed since `#npQueue` (part of the `.left` control set already visible on Library/Search anyway) already covers the same purpose.

- **Layout instead of overlay**: `.pages` and `#queuePanel` are flex siblings inside a new `.main-row` container (which now takes over the role `.pages` alone used to have: `flex: 1; min-height: 0;` as the middle row of `.wrap` between `.top` and `#playbackBanner`/`.footer`). `#queuePanel` itself is `width: 0; overflow: hidden;` when closed, `.queue-panel.open { width: 360px; }` when open (`max-width: 90vw` as a safety net on narrow screens) — a CSS `transition: width`. Since `.pages` carries `flex: 1; min-width: 0;`, it automatically shrinks by exactly the amount `#queuePanel` grows, instead of the panel covering the content. `#playbackBanner`/`.footer` deliberately sit **outside** `.main-row` (direct children of `.wrap`) and therefore always stay full width, regardless of the panel's state.
- This also does away with the earlier `syncBannerQueueOffset()`/`resize` pairing entirely: `.main-row`, being a `flex: 1` element, always fills exactly the space between `.top` and `#playbackBanner`/`.footer`, with no header/footer/banner-height pixel values ever needing to be reconciled anywhere.
- Inside the panel, everything runs unchanged through the existing queue logic: `#queue` (the same list, `loadQueue()`/`renderQueueRows()`/`queueRow()`/`tryQueueSlide()` from the "Cover crossfade and queue slide" section) plus the reload/clear buttons in `#queueToolbar` (`#bQueueReload`/`#bQueueClear`) — none of it was duplicated, only the surrounding panel is new. `#queueToolbar` also carries the Radio Mode button (`#bQueueRadio`, see "Radio Mode").

- `paintQueueToggle()` keeps every existing trigger button (`npEls('npQueue')`) in sync in its `.on` state (accent color), no matter which one opened the panel.
- **No click-outside-to-close**: since the panel is now real layout space instead of an overlay, there's deliberately no click-outside-closes listener anymore (unlike the header dropdowns, see `closeStationMenu()`) — only `#queuePanelClose` or tapping an `#npQueue*` button again (which toggles) closes it.

Jumping back in the queue (playing an already-played track) forces a full rebuild instead of the slide animation (`tryQueueSlide()` deliberately bails out on a negative `shift`), so the rows that are now "upcoming" again below the new position reliably lose their `played` class.

## Dark/Light mode

All colors in the `<style>` block are defined as CSS custom properties on `:root` (`--bg`, `--bg-elevated`, `--bg-elevated-2`, `--surface`, `--surface-active`, `--border`, `--text`, `--text-dim`, `--text-secondary`, `--text-muted`, `--text-faint`, `--accent`, `--danger`, `--fav`, `--fav-border`; theme-independent constants: `--on-accent`, `--on-danger`, `--success`). No single color value may appear as a hex literal anywhere in the CSS or inline styles — always define new rules via `var(--...)`, otherwise the theme breaks at that spot.

Three levels determine the active value set, in ascending priority:

1. `:root` supplies the dark values as the base (no attribute needed).
2. `@media (prefers-color-scheme: light) { :root:not([data-theme]) { … } }` overrides to light when the system is set to light and no explicit choice has been made.
3. `:root[data-theme="light"] { … }` overrides explicitly, regardless of the system, as soon as `<html>` carries the `data-theme="light"` attribute (dark needs no `[data-theme="dark"]` block of its own, since that's already the base of `:root`).

On the JS side (`THEME_STORAGE_KEY = 'ma-dashboard-theme'`, starting from `detectTheme()`), a saved choice is read from `localStorage`, the `data-theme` attribute on `document.documentElement` is set/removed accordingly, and the icon (`#themeSwitch`, moon/sun depending on `effectiveTheme()`) as well as `<meta id="themeColorMeta" name="theme-color">` are kept up to date. Tapping `#themeSwitch` (`toggleTheme()`) always sets an explicit choice that permanently overrides the system — there's deliberately no UI path back to "automatic", only a new manual choice. A `matchMedia` listener keeps the icon/meta current if the system setting changes while no explicit choice has been saved yet.

A small inline `<script>` right in `<head>` (before the cache-busting script for `ma-env.js`) applies a saved choice before the first paint, so the wrong theme doesn't briefly flash on load.

The accent color `--accent` itself is deliberately *not* constant between themes (dark `#ffffff`, light `#6b6b66`): it's used in the UI both as a background surface (with `--on-accent` text) and directly as a text color; against a light background, bright white as text would have too little contrast, hence a medium, noticeably darker gray in the light theme.

## Accent color

The user can choose the accent color via a color wheel in the header (`#accentSwitch`). The popover (`#accentMenu`, swatches in `#accentSwatches`, rendered by `renderAccentSwatches()`) shows five tappable circles: **"Dynamic"** first (a rainbow swirl instead of a flat color — see below), then the fixed preset palette (`ACCENT_PRESETS`, defined in the early inline `<script>` in `<head>`, default `ACCENT_PRESETS[0]` = White `#ffffff`: White, Blue, Light Blue, Light Orange). Deliberately no free color picker (no `<input type="color">`) — unsupported by Safari 9; a fixed palette of tappable swatches works reliably on every iOS version.

- `ACCENT_STORAGE_KEY = 'ma-dashboard-accent'` in `localStorage` holds either a preset hex value, the sentinel `'dynamic'`, or nothing (= default); `currentAccent()` returns one of these three states.
- Unlike the theme, the accent color is **not** set directly via `document.documentElement.style.setProperty(...)` — as an inline style on `<html>`, that would overwrite both the dark and the light variant at once and break the three-level cascade from "Dark/Light mode". Instead, `applyAccentOverride()` injects a `<style id="accentOverrideStyle">` element into `<head>` for an actual preset choice, reproducing exactly the same three-level `:root` / `@media (prefers-color-scheme: light)` / `:root[data-theme="light"]` structure for `--accent` — just with the chosen color instead of the defaults. On returning to the default preset **or** to `'dynamic'`, the style content is simply cleared, letting the defaults baked into the main CSS take over again (in the Dynamic case, possibly overridden again by `applyTrackAccent()`).
- `deriveLightAccent(hex)` (RGB→HSL→RGB, all helpers likewise in the early `<head>` script) automatically computes the light-theme variant for the other three presets by scaling lightness to 78%. That's not enough for "White" (the default): 78% of an already-100% lightness still yields a very light gray, too little contrast as body text on a light background. The default therefore gets a hand-picked light-theme counterpart instead of the plain formula, the same way it did before the switch to the four new presets (`#6b6b66`, a medium gray) — see the comment right next to `ACCENT_PRESETS`.
- `applyAccentOverride()` is called both from the early `<head>` script (FOUC avoidance, same principle as the theme) and from `setAccent()` in the main script; both places share the same global function instead of duplicating the color math.
- **"Dynamic" — live color from the artwork**: `applyTrackAccent(hex)` (also in the early `<head>` script, right next to `applyAccentOverride()`) reproduces the same three-level structure in its own `<style id="trackAccentStyle">` element — **but only when `ACCENT_STORAGE_KEY === 'dynamic'`**; for any static preset the call is a no-op, so the preset stays put regardless of what's currently playing. Since this element is only created at runtime, on the first cover with artwork, and is therefore always inserted into `<head>` *after* `accentOverrideStyle`, a color extracted from the current cover (see "Now Playing: full screen and gradient") automatically wins over `accentOverrideStyle` (which is empty anyway by then) while in Dynamic mode — pure CSS ordering, no `!important` needed. `applyTrackAccent(null)` (no artwork, a tainted canvas, or simply not in Dynamic mode) clears the style content, letting the default take over.
- The `#accentSwitch` dot in the header does **not** get a JS-computed hex value as its background in Dynamic mode, but literally the CSS reference `var(--accent)` (`updateAccentSwitchUI()`) — the browser keeps this automatically in sync with every change to `--accent`, with no JS needing to run again on every track change. For a static preset it's still simply that preset's hex value.
- `setAccent('dynamic')` immediately re-samples the cover that's already loaded (`lastCoverSrc`, if any) via `updateNowGradient()`, rather than waiting for the next track change. Conversely, when leaving `'dynamic'` (or switching between two presets), `setAccent()` cleans up `trackAccentStyle` via `applyTrackAccent(null)` — otherwise a previously set track color would keep sitting above the newly chosen preset, purely due to `<head>` ordering.
- The transport icons (`svgIcon('prev'|'next'|'play'|'pause')`) use `style="fill:var(--accent)"` instead of a hardcoded hex value, so they automatically follow both the preset choice and the Dynamic color.
- The popover menu follows the same open/close pattern as `#stationMenu`/`#groupMenu`/`#settingsMenu` (see `document.addEventListener('click', …)` further down in the file) — all four menus close each other when one of them opens.

## Favorite asymmetry

MA deliberately treats favorites asymmetrically:

- **Adding** goes through `music/favorites/add_item` with the item's URI.
- **Removing**, on the other hand, needs `media_type` + `library_item_id` from the library item.

The dashboard therefore resolves the item via `music/item_by_uri` before every favorite action. That's the only reliable way to know whether the item is in the library and whether `favorite` is already set.

## Library items and provider resolution

Items from the library (`music/<type>s/library_items`) carry `provider === 'library'` instead of a real streaming-provider domain. `music/artists/artist_albums`/`artist_tracks`, when called with `provider_instance_id_or_domain: 'library'`, returns server-side only the entries already linked into the library (a plain DB query), not the provider's full discography.

`resolveProviderRef(it)` therefore resolves library items through `it.provider_mappings` (a required field on every MA media object) to a real provider, returning `{ item_id, provider_instance_id_or_domain }` for the actual streaming provider. `openArtist()` uses this so "Top tracks"/"Albums" show the full list even when navigating in via the library, instead of only the few entries already linked there.

## Images and the image proxy

MA supplies a `proxy_id` for every medium. Via `/imageproxy/<proxy_id>?size=<n>&fmt=jpeg`, the server scales the image to the requested edge length. This is essential on old iPads, since original covers can be several megabytes.

The image proxy only accepts the sizes `{0, 80, 160, 256, 512, 1024}`; other values result in HTTP 400. `CFG.IMG_COVER` and `CFG.IMG_THUMB` must therefore be set to one of these values (default: 512 for covers, 160 for thumbnails). If no `proxy_id` is present, the legacy URL `/imageproxy?path=…&provider=…` is used as a fallback.

If `current_media.image_url` comes from a misconfigured internal `base_url` on the MA server (typical with a reverse proxy or Docker), the host for proxy URLs is rewritten to `CFG.MA` (`fixUrl`).

## Homescreen web clip and update detection

As an "Add to Home Screen" app (`apple-mobile-web-app-capable`), WebKit on iPads often stubbornly clings to a once-loaded snapshot of `ma-dashboard.html` — the `<meta http-equiv="Cache-Control">` tags in `<head>` aren't enough for this, since they can only replace real HTTP response headers when the server itself doesn't set any, and web-clip mode has its own, more aggressive rules. Without a countermeasure, new versions only show up after manually deleting and re-adding the homescreen icon.

To counter that, there's `checkForUpdate()`: at startup, on returning from the background (`visibilitychange`), on `pageshow`, **and periodically every `UPDATE_CHECK_INTERVAL_MS`** (default 10 minutes, `setInterval(checkForUpdate, UPDATE_CHECK_INTERVAL_MS)` alongside `setInterval(tick, 500)`), `ma-dashboard.html` is freshly fetched from the server via `XMLHttpRequest` with a cache-busting query string (`?_v=<timestamp>`) and explicit `Cache-Control`/`Pragma: no-cache` request headers, and the `APP_VERSION` constant found in it via regex is compared against the one currently running. If it differs, a toast appears and, after a short delay, a hard navigation (`location.href`) to a new URL (a different query string) follows, so WebKit doesn't serve the cached version again.

The periodic timer is the actually reliable path, not just a supplement: this app is meant as a permanently visible kiosk display (a wall-mounted iPad, with `setInterval(tick, 500)` running continuously for the progress bar). Such a device may well go weeks without ever truly backgrounding or navigating anew — `visibilitychange`/`pageshow` simply stop firing then, and without the interval timer, update detection would be effectively dead despite the JS context demonstrably still running. If the file is additionally served via a route with a long-lived `Cache-Control` (e.g. Home Assistant's `/local` static route for files in the `www/` directory, known for fairly long cache times), that further favors a stale version on the very first load — that's not fixable server-side from this repo, hence the purely client-side, event-independent polling approach.

**Important:** `APP_VERSION` (near the top of the `<script>`, before the "CONFIGURATION" section) must be bumped on every functional change to `ma-dashboard.html` — otherwise the mechanism won't detect a new version and the web clip stays on the old one despite deployment.

## Development and customization

- Make changes only in `ma-env.js`; everything else normally shouldn't need to be touched.
- `ma-env.js` is excluded via `.gitignore`; don't commit changes to it.
- Add new media types or API endpoints to `NAVIGABLE`, `GROUPS`, `LIB_TYPES` and the detail functions (`openArtist`, `openAlbum`, `openPlaylist`, `openPodcast`).
- Tabs in detail views are modeled in the view object as `tabs: [{ key, label, load }]`, `activeTab` and `cache`.
- "Add to playlist" extends the action sheet; new UI elements must stay ES5-compatible.
- In the "Add to playlist" sheet, `renderPlaylistList()` groups by provider (`itemProviderDomains()`/`sourceLabel()`, the same helpers as the music-source filter), sorted alphabetically by provider name. Within a group, `playlistSortMode` (chips from `renderPlaylistSortFilters()`, values `'recent'`/`'alpha'`) determines the order — `comparePlaylistsRecent()` sorts by `timestamp_added` descending (MA's time of adding to the library), `comparePlaylistsAlpha()` sorts alphabetically by name. `loadUserPlaylists()` itself no longer pre-sorts server-side; the full grouping/sorting happens client-side in `renderPlaylistList()`.
- The Collection tab calls `music/<type>s/library_items` without a `favorite` filter, so every item carries the `favorite` flag and `mediaRow()` can show the heart. A "Favorites only" toggle chip filters the list client-side.
- Group-member volume: members are determined from `group_members`/`group_childs`, or as a fallback via `synced_to`/`active_group`. Every member that has `supported_features` gets its own slider under the main volume slider.
- `rebuildPlayerOrder()` consistently excludes group members from `playerIds` — it checks `p.synced_to`, `p.active_group`, AND whether the id shows up in another player's `group_members`/`group_childs`. Some MA players only mirror their membership on the group leader, not on themselves; if that's not accounted for, such a member stays in `playerIds` and often also reports `state: 'playing'` via `players/all` — which used to make a second "active" station briefly appear next to the actually selected player in the header on load (`buildStations()`).
- Grouping menu: `resolveGroupMembers(id, filterVolume)` is the shared basis for group members — with `filterVolume=true`, `getGroupMembers()` returns only volume-capable members (for the volume sliders); with `filterVolume=false`, `renderGroupMenu()` returns all members (for display/removal). Candidates for adding are filtered out of `playerIds` by `set_members` in `supported_features`.
- Tab origin on detail navigation: `enterDetail()` remembers in `navOriginTab` which footer entry (typically Collection) a detail view was opened from, and passes that to `switchTab(name, pillName)` as the second parameter, so the originating entry stays visually active even though the detail view technically always runs through `switchTab('search', …)` in `#paneSearch` (inside `#pageLibSearch`). `popView()` switches back to `navOriginTab` once the navigation stack empties out. New navigation entry points into detail views should use `enterDetail()` rather than a direct `switchTab('search')`.
- New footer pages: add an entry to `TABS` (`{ pane, init }`), add a `<div class="tab" data-tab="…">` icon to `.footer` and a `#page…` container to `.pages` in the HTML, add the icon to `svgIcon()`, and set it at boot via `$('foot…').innerHTML = svgIcon(…)` (see "Page router (footer navigation)").
- Sorting: `sortMediaItems(items, mode, dir)` (modes `'name'`/`'year'`/`'albumArtist'`/`'lastPlayed'`/`'playCount'`, with `'year'` falling back to `item.album.year` for tracks with no year field of their own; `dir` optional, `-1` reverses the given mode's result, anything else/omitted behaves as before) is the shared sort helper for the Collection page (`libSortMode`/`libSortDir`), Search (`searchSortMode`, additionally `'relevance'` as the server order, no `dir`), and the "Tracks"/"Albums" tabs of the artist view (`artistSortMode`, applied in `renderActiveSections()`, likewise no `dir`). The Collection page and the artist view draw from **different** constants here: `LIB_SORT_MODES` (the full five-item list, only for the Collection chips) and the smaller, still-shared `SORT_MODES` (`Name`/`Year`, for the sort chips in `renderTabs()`) — album-artist/last-played/play-count sorting doesn't fit the track/album list of a single artist as conceptually well. Tabs in the view object carry a `sortable` flag for this; "Top tracks" is deliberately `sortable: false`, since its order is the popularity ranking. Not applied in the shared `renderSections()`, since that's also used by detail track lists with a fixed order (track numbers, playlist order).
- Default player selection: `pickDefaultPlayer()` (used in `bootstrap()`) only adopts `CFG.DEFAULT_PLAYER` when `isPlayerUsable()` holds (`available`/`enabled` not `false`); otherwise the first player in `playerIds` with `state === 'playing'` is chosen (groups are recognized via their leader here, see the `synced_to` filtering in `rebuildPlayerOrder()`), otherwise the first one in `playerIds`.
- Make UI changes only with ES5-compatible CSS and JS.
- Don't add external libraries; the file should remain self-contained and runnable on its own.

## Troubleshooting

- **"Login rejected"** — check `CFG.TOKEN`; the token must be long-lived and have at least the `user` role.
- **"This browser can't do WebSocket"** — the iPad/Safari is too old; iOS 9.3 minimum required.
- **Connection light stays red** — check `CFG.MA`, make sure the MA server is reachable, watch for firewall/WebSocket-proxy issues. Tapping the light itself (`#link`, `pingServer()`) sends a quick HTTP round-trip to `CFG.MA`'s `/info` endpoint (the same lightweight, CORS-enabled one `probeClock()` already uses for clock correction) and reports the round-trip time or the error as a toast — not a real ICMP ping (browsers can't send one), just a fast reachability check without digging into the browser's network tab. Works regardless of the light's current color.
- **Bar doesn't keep up** — see the "Progress bar and the beta bug" section; not a client bug, but expected server behavior.
- **Images don't load** — `CFG.MA` must be correct; with a reverse proxy, `/imageproxy` must be reachable.
- **Homescreen app shows an old version** — check whether `APP_VERSION` was actually bumped on the last deployment (see "Homescreen web clip and update detection"); without that, `checkForUpdate()` won't detect a new version. A homescreen icon installed before the periodic update check (`UPDATE_CHECK_INTERVAL_MS`, introduced in this version) needs a **one-time** manual reset (delete the icon → reload in a Safari tab with a cache-busting query → re-add the icon); after that, the app will update itself on its own at least every `UPDATE_CHECK_INTERVAL_MS`, even without ever backgrounding/foregrounding.
- **Theme doesn't follow the system setting** — usually there's already an explicit manual choice in `localStorage` (`ma-dashboard-theme`) permanently overriding the system (see "Dark/Light mode"); delete that entry to switch back to automatic.
